## 3. 拆分原则（关键）

1. **保持提交顺序，不重排、不跳选**。19 个提交在原始分支上已是线性、互相依赖的（如 2.1 导演是 2.2/2.6 的前置；5.1 多 Provider 是 5.2 的前置；每个 Phase 都向 `engine/src/daemon/handlers.rs`、`daemon/mod.rs`、`agent/mod.rs`、`lib.rs`、`webui/assets/console-runtime.js`、`webui/tests/runtime-pages.test.mjs` 等"枢纽文件"做**追加式注册**）。只要按原顺序、连续区间切片，依赖与编译天然满足。
2. **用 `git cherry-pick <区间>` 在复现分支上重放，而非 `rebase --onto`**。在"上一组已合入 main"的前提下，对下一组提交做 `git cherry-pick <lower>..<upper>`（下限已合入、被排除；上限含入），按顺序重放即等价于 rebase 重放，树状态完全一致、**预期零冲突**，且命令更直观、每提交历史可见。关键纪律：必须等上一组 PR 合入 main、并 `git fetch` 后基于 `origin/main` 新建下一组分支，否则枢纽文件会因合并基错位产生假冲突。
3. **每 PR 一个 Phase（或连贯子区间）**，按路线图"每阶段可独立发版"的单元切分。
4. **分支名用扁平名**（如 `split-phase1`），**禁止 `feat/xxx` 嵌套名** —— 本机 `.git/refs/heads/` 子目录创建不稳定（见工作记忆 2026-07-23），嵌套名会触发该坑。

## 5. 执行步骤（cherry-pick 复现，机械流程）

> 全程在本地执行；每步完成后**立即 push**，避免 refs 不稳定丢引用。
> **铁律**：每组 PR 必须先在 GitHub 合入 main，再 `git fetch origin` 后基于 `origin/main` 新建下一组分支。禁止在未合入前并行建分支——否则枢纽文件（见 §3.2）会因合并基错位冲突。
> 命令中 `git cherry-pick <lower>..<upper>` 重放区间 `(lower, upper]`，下限须为已合入 main 的提交（被排除）。

## 8. 风险与注意

- **git refs 不稳定**：本机 `.git/refs/heads/feat/...` 子目录曾无法落盘。全程用**扁平分支名**（`split-phaseN`），每步 push 后立即确认远端存在；若本地 `.git/refs` 消失，按工作记忆手工 `echo <sha> > .git/refs/heads/<branch>` 重建。
- **枢纽文件假冲突**：严格按顺序合并 + 基于 `origin/main` 建分支的前提下，cherry-pick 理论零冲突；若极个别出现（多为漏做 `git fetch` 导致基于旧 main），因均为追加式注册，解决原则 = 保留双方新增行（handler 注册 / `pub mod` / 屏数自增）。
- **勿重排提交**：Phase 2 内部（导演→NPC/辩论）、Phase 5（多 Provider→Ollama）有前置依赖，必须连续合入，不可把 PR B/E 拆散或调序。
- **审计遗留项**：每个 PR 合并后，按 `AGENTS.md` 时序约束——审计遗留的"未改动但写出的修改意见"在**合并后**整理进对应 issue（去重 + 标来源 PR 与原编号）。
