## Blocking finding and resolution

### B1 — TypeScript accepted unsupported successful Workspace documents

The initial client parser accepted arbitrary integer workspace/layout majors
and arbitrary non-empty Widget types. A successful response containing a
future major could therefore enter the typed client path even though the
contract permits future-major data only through raw export.

Resolved before submission. The parser now enforces Workspace/layout major 1,
the closed first-party Widget allowlist, bounded identifiers and timestamps,
node/depth/children/Widget limits, duplicate IDs, placement/reference parity,
and valid active-tab references. Regression tests reject future-major and
non-allowlisted successful documents.

## Additional checks

- Router-wide bearer validation executes before Workspace extraction; handlers
  additionally fail closed when daemon authentication is not configured.
- Effective roots are derived only through validated `UserId`; no request path,
  workspace ID, filename, or revision directory is accepted.
- The reducer reads, transforms, validates, and commits under the Workspace
  lock. CAS failure, invalid target, invalid ratio, and oversized body do not
  publish a revision.
- Future-major read is a structured 409 while raw export remains byte-exact and
  includes no-store, schema, and SHA-256 headers. CORS exposes all verification
  and download headers.
- HttpEngineBus preserves the public structured error fields and does not replay
  a 409 mutation.
- Client history parsing also rejects a response larger than the server's 256
  entry contract.

## CI review amendment

CodeRabbit subsequently identified that the client used identifier syntax for
history `updated_at`, rejecting Engine-generated RFC3339 offsets such as
`+00:00`. This was fixed before merge by using the same bounded-string rule as
the Workspace document timestamp, with a regression fixture containing the
numeric UTC offset. The finding is closed.
