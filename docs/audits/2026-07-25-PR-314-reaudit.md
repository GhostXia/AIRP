## 2. 阻塞项（必须修复后重审）

### B1. Analysis 文件列表把对象当字符串处理 —— Phase 1.6 完全不可用

**位置**：`webui/assets/console-runtime.js:231-261`

**证据**：

Engine `AnalysisFileList`（`decompose_handlers.rs:51-55`）返回 `files: Vec<AnalysisFileEntry>`，每个元素是 `{filename: String, size: u64}` 对象（`decompose_handlers.rs:57-61`）。WebUI 代码：

```js
const files = list.files || [];
files.forEach(filename => {                       // ← filename 实为 {filename,size} 对象
  row.appendChild(node('div', 'runtime-row-title', filename));   // 渲染 "[object Object]"
  ...
  client.request('GET', '.../analysis/' + encodeURIComponent(filename));  // → /analysis/[object%20Object] → 404
});
```

**后果**：① 列表每行显示 `[object Object]`；②「查看」「Enhance」请求 URL 编码为 `/analysis/[object%20Object]` → Engine 返回 404。Phase 1.6 的文件浏览功能完全不可用。

**修复**：`files.forEach(entry => { const filename = entry.filename; ... })`，后续 `encodeURIComponent(filename)` 与 `node(..., filename)` 均用 `entry.filename`。

**独立性备注**：前次审计 B1 的判定**正确**，本复审独立验证后确认仍有效。CodeRabbit 的 CR-2 提到 stale apply button 问题（见 §3 N-C）但未指出 B1 这个根本性对象当字符串缺陷。

### B2. 场景添加角色：WebUI 角色词表与 Engine 枚举不匹配 —— 3/4 选项 400

**位置**：`webui/assets/console-runtime.js:487`

**证据**：

Engine `CharacterRole`（`scene.rs:8-14`）：

```rust
#[derive(...)]
#[serde(rename_all = "snake_case")]
pub enum CharacterRole {
    Primary,
    #[default]
    Npc,
}
```

serde 默认对未知变体返回 400。WebUI 下拉：

```js
input('角色类型', 'main', { select: [
  { value: 'main', label: '主角 (main)' },
  { value: 'supporting', label: '配角 (supporting)' },
  { value: 'npc', label: 'NPC' },
  { value: 'narrator', label: '旁白 (narrator)' }
]});
```

`main`/`supporting`/`narrator` 三个值在 Engine 端不存在 → `POST /v1/scenes/:id/characters` 返回 400 反序列化错误。仅 `npc` 可用。Phase 1.3 场景加角色在 3/4 选择下失败。

**修复**（PR 声明「无 Rust 改动」，故对齐 WebUI 到 Engine 契约）：下拉改为 `primary`/`npc`（标签「主角 / NPC」）；或若确需 supporting/narrator，应在 Engine 扩展枚举（超出本 PR 范围，需另立 PR 并补测试）。

**独立性备注**：前次审计 B2 的判定**正确**，本复审独立验证后确认仍有效。

### B3. 对话导出静默截断 —— 长对话丢消息（数据完整性）

**位置**：`webui/assets/chat-space.js:608`

**证据**：

WebUI 发送 `limit: 9999`：

```js
const data = await client.request('POST', '/v1/chat/history', { character_id: characterId, session_id: sessionId, limit: 9999 });
```

Engine handler（`daemon/handlers/chat.rs:32-45`）：

```rust
if query.limit.is_some() || query.before.is_some() {
    let window = ChatService::new(&state.data_root).history_window(...)?;
    return Ok(Json(serde_json::to_value(window)?));
}
// legacy 全量返回 ...
```

`history_window`（`domain.rs:228`）：`let limit = limit.unwrap_or(50).clamp(1, 200);` → 9999 被钳为 200。且**无 `before` cursor 时返回尾部最近 limit 条**（`domain.rs:274-279`）。

**后果**：会话消息 >200 条时，导出只保留**最近 200 条**、静默丢弃更旧消息。对一个标称「对话导出（Markdown/JSON）」的功能是静默数据丢失，违背项目「不破坏用户资产」底线。

**修复**（前次审计建议正确，本复审独立验证）：导出走 legacy 全量路径——**不传 `limit` 字段**。`HistoryQuery.limit: Option<usize>`（`types.rs:241`），不传时 `query.limit = None`，handler 走 `else` 分支返回完整 `ChatLog`（含 `messages` 与 `message_timestamps`，`chat_store.rs:39,55`）。或在 UI 明确提示「仅导出最近 N 条」。推荐前者。

## 4. 对 CodeRabbit CR-9 的反驳

CodeRabbit CR-9 称：

> 修正 B3 的"去掉 `limit` 即全量导出"建议。`history_window` 的契约是 `limit.unwrap_or(50).clamp(1, 200)`，且无 `before` 游标时只返回末尾窗口。因此不传 `limit` 会导出最近 50 条，而不是完整会话。

**本复审独立查证后判定：CR-9 错误，前次审计 B3 修复建议正确。**

证据（`handlers/chat.rs:32-45`，本代理亲自读完）：

```rust
if query.limit.is_some() || query.before.is_some() {
    let window = ChatService::new(&state.data_root).history_window(
        &query.character_id, query.session_id.as_ref(),
        query.limit, query.before.as_deref(),
    )?;
    return Ok(Json(serde_json::to_value(window)?));
}
// legacy 全量返回必须保留 ChatLog 的既有响应形状。
let log = ChatService::new(&state.data_root)
    .history(&query.character_id, query.session_id.as_ref())?;
Ok(Json(serde_json::to_value(log)?))
```

CR-9 误读了条件分支：`unwrap_or(50).clamp(1, 200)` **只在 `history_window` 内**，而 `history_window` **只在 `query.limit.is_some() || query.before.is_some()` 时被调用**。当 WebUI **不传 `limit`** 字段时，`query.limit = None`（已验证 `HistoryQuery.limit: Option<usize>`，`types.rs:241`），handler 走 `else` 分支 → 调 `history()` 返回**完整 `ChatLog`**（含 `messages` 与 `message_timestamps` 全量数组）。

因此前次审计 B3 的修复建议（"不传 limit"）**完全正确**。CR-9 的反驳基于对条件分支的误读，应予驳回。

## 5. 非阻塞项（记录，建议后续迭代）

### N-A（新）：decompose_handlers.rs:82 陈旧注释误导审计

`decompose_handlers.rs:78-83` 注释仍写「enhanced_md 由 LLM 生成，当前实现先返回原内容占位」，但 L293 实际已调 `enhance_md_via_llm`。这正是前次审计 N5 误判的根源。建议更新注释为：「enhanced_md 由 LLM 真实生成（issue #92 L3 修复）」。

### N-B（CodeRabbit CR-1）：HUD 把所有数值字段当 0-100 百分比

`chat-space.js:562-571`：

```js
if (typeof value === 'number') {
  fill.style.width = Math.min(100, Math.max(0, value)) + '%';
  ...
}
```

`/v1/characters/:id/state` 返回任意 live JSON，数值字段可能是 0-1（如 `mood: 0.85`）、1-10（如 `level: 7`）、>100（如 `hp: 250`）等任意刻度。当前实现：
- `0.85` → 进度条 `0.85%`（几乎不可见，误导为"极低"）
- `7` → 进度条 `7%`
- `250` → 钳为 `100%`

**建议**：仅对已知百分比字段（如带 `_percent`/`_pct` 后缀或 schema 标注 0-100）渲染进度条；其余数值按原值显示。或从 `state/schema` 端点读字段范围。

### N-C（CodeRabbit CR-2）：Stale "应用 Enhance 结果" 按钮累积

`console-runtime.js:239, 247` 的 View/Enhance handler 只删除 `.analysis-content`，不删除 `.analysis-apply` 按钮。连续 Enhance 不同文件会堆叠多个无标签 apply 按钮，用户无法区分。

**严重度备注**：CodeRabbit 标 Major 略高。每个 apply 按钮的闭包正确捕获各自的 `filename` 与 `result.enhanced_md`，不会跨文件污染（点 A 的 apply 按钮只会 apply 到 A）。属 UX 混乱，非数据损坏。建议按 CodeRabbit 提供的 diff 修复：增加 `.analysis-apply` class，View/Enhance 时一并清除。

### N-D（CodeRabbit CR-3）：场景元信息异步获取的竞态

`console-runtime.js:501-503`：每行 fire-and-forget `client.request('GET', .../scenes/id).then(scene => meta.textContent = ...)`。若用户在初始 fetch resolve 前点「+角色」并完成添加，初始 fetch 的 stale 响应会覆盖刚刚刷新的 meta。**严重度：UX 瑕疵，无数据丢失**。建议按 CodeRabbit 提供的 `metaVersion` token 方案修复。

### N-E（CodeRabbit CR-4）：Bearer token 可能泄漏给 query-controlled engine origin

`relationship-graph.js:5-9` 从 URL `?engine=` 读取并写入 sessionStorage，`api-client.js:140` 对所有请求加 `Authorization: Bearer ...`。攻击者构造 `?engine=https://evil.com` 诱导用户点击后，用户的 bearer 会随每个 API 请求发往 evil.com。

**重要备注**：这是**全 WebUI 既存模式**（`chat-space.js`、`console-runtime.js` 等所有屏幕均如此），**非本 PR 引入**。本 PR 只是延续既有模式新增一个屏幕。**不构成本 PR 的阻塞**。但建议在 `api-client.js` 层做应用级修复：仅对同源或白名单 origin 发送 bearer，跨源时剥离。可作为独立 issue 跟进。

### N-F（CodeRabbit CR-5）：`intensity: 0` 被默认值 0.5 覆盖

`relationship-graph.js:50`：`intensity: (val && val.intensity) || 0.5`。`0 || 0.5` 在 JS 中求值为 `0.5`（0 是 falsy），丢失显式零强度。**建议**：`(val && val.intensity != null) ? val.intensity : 0.5`。

### N-G（前次 N6 = CodeRabbit CR-6）：rAF 循环空转

`relationship-graph.js:157-161`：`tick()` 在 `simRunning=false` 且无图时仍每帧 `requestAnimationFrame` 重绘，空闲也持续占用 CPU/GPU。**建议**：布局稳定后停止 rAF，交互/resize/数据加载时再启动。

### N-H（CodeRabbit CR-7）：角色切换后导航链接未刷新

`relationship-graph.js:224`：`sel.addEventListener('change', ...)` 仅更新 `characterId` 与 sessionStorage，未调用 `renderChrome()`。导航链接（由 `pathWithState` 在 boot 时构建）保留旧 `?character=...`，跳转后会回到旧角色。**建议**：change handler 中调用 `renderChrome()` 重建链接。

### N-I（CodeRabbit CR-8）：关系图谱缺少 canvas 的可访问性替代

`34-relationship-graph.html` 仅用 `<canvas>`，未提供语义化表格/列表供屏幕阅读器读取 source/target/type/intensity。**建议**：在 canvas 旁加 visually-hidden 的 `<table>` 或 `<ul>`，数据加载时同步更新。

### N-J（前次 N3）：拆分计划文档仍缺失

PR 正文引用 `docs/progress/2026-07-25-split-PR313-plan.md`，但仓库中仍不存在（`Glob` 确认）。拆分理由与合入顺序无法溯源。建议补文档或移除引用。

`runtime-pages.test.mjs` 仅校验「文件数=34」与「无内联 `style=`」。233 行的力导向图（物理模拟/canvas 绘制/拖拽）、chat-space.js 的 HUD/导出逻辑、console-runtime.js 的 Analysis 面板**无任何行为测试**。建议补 jsdom/canvas 冒烟或契约测试。

### N-L（前次 N7）：HUD 轮询错误被静默吞掉

### N-M（本复审独立发现）：节点边框使用 `--text-inverse`（白色）不可见

`relationship-graph.js:144`：`ctx.strokeStyle = COLORS.inverse;`（`--text-inverse: #FFFFFF`，白色）。节点填充为 `--primary: #C4663B`（暖橙），画布底为 `--bg-base: #FAFAF7`（米白）。白色 2px 边框在橙色节点与米白底之间**几乎不可见**，节点失去边框定义。
