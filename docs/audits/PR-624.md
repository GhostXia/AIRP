## Final verdict

**PASS.** No blocking finding remains. The HTTP adapter exposes only the
bounded Blueprint-v1 migration transaction established by PR #617. It does not
accept arbitrary Workspace documents, paths, backup scopes, candidates, or
JSON Patch.

## Audit conclusions

- The three migration routes remain inside the daemon bearer-authenticated v1
  router.
- Request envelopes and Blueprint source/theme/layout/area/widget structures
  reject unknown fields. Legacy `props` values and theme token names retain
  their intended open value/map boundaries but are not migrated into the saved
  Workspace.
- Workspace revisions use the string-only `SurfaceRevision` contract.
- Every route uses the protocol-owned 262,144-byte whole-request limit.
- An outer route-aware middleware adds `Cache-Control: no-store` after
  rate-limit, authentication, extraction, and handler responses, including
  success and error outcomes.
- Apply recomputes and binds the normalized typed-source hash, candidate hash,
  converter version, and current Workspace CAS. The source hash is not
  described as an original-upload byte hash.
- Effective roots and user IDs are validated. Migration backup IDs are
  validated as one safe path segment before disk lookup, and backup scope plus
  approved bytes are revalidated under the backup lock.
- Cross-root backup IDs are not visible, tampered backups fail closed, and an
  unsupported future Workspace major prevents apply without creating a backup.
- Revision-zero recovery and committed-layout recovery both publish a higher
  forward revision; generic destructive restore remains excluded.
- Definite commit failure and outcome unknown preserve their distinct stable
  error code, recovery category, and retained backup ID without exposing paths
  or internal diagnostics.
- Filesystem migration and rollback execute in `spawn_blocking`, and the
  `WORKSPACE_LOCK -> BACKUP_LOCK -> revision COMMIT_LOCK` order is unchanged.
- This PR changes no Vue/WebUI implementation. Existing saved split ratio,
  dynamic projection, and responsive-layout tests remain passing.

## Non-blocking follow-ups

1. **Low / engine async boundary:** user-scoped route setup resolves the
   effective root before entering `spawn_blocking`; that resolver may create
   user directories and briefly block an async worker on a slow filesystem.
   Move effective-root resolution into the blocking operation when next
   refactoring Workspace HTTP adapters.
2. **Low / HTTP test matrix:** `no-store` is structurally applied to all three
   exact paths and is directly covered for 200, 400, 401, 413, 500, and 503.
   Add explicit 404, 409, and 429 assertions to protect middleware placement
   against future route-layer changes.

These do not affect the current single-process data-integrity or security
claim. Per repository policy, unresolved audit suggestions are filed as
deduplicated GitHub issues only after the PR is merged.
