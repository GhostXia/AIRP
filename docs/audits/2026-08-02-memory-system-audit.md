## 1. 项目概况

- **定位**：专精 Role Play 的 AI Agent 客户端；采用“无头 Engine + 可换 UI”结构，把角色、Persona、Preset、Worldbook、会话、记忆、Agent 执行和安全边界集中在一个可审计的本地数据面。
- **技术栈**：
  - 引擎：`airp-core`（Rust），提供 HTTP/SSE 服务；OpenAI-compatible / Anthropic / Ollama 多 Provider 路由。
  - 前端：当前正式主面 `webui/`（无构建 WebUI，44 屏）；保留的桌面端 `ui/`（Tauri + Vue，近期发布暂停）。
  - 协议：`protocol/`（共享线协议）；Rust Cargo workspace + npm 前端。
- **成熟度**：公开基线 2026-07-30，`main@4f3f792`；仍是 **P1 有限试用代码候选**，非正式发布。
- **核心原则**：
  - RP 角色 prompt 只包含 RP 数据；工具、调度、审计留在结构化控制平面。
  - Engine 是数据和业务规则的单一真相；UI、handler、Agent tool 不复制持久化规则。
  - 用户资产必须可迁移、验证、导出、回滚。
  - 只吸收第三方公开理念，独立实现，不复制第三方代码/prompt/测试/资产。
  - 本地测试全绿才可开 PR；审计 bot 通过、阻塞意见修复并经人工 review 后才能合并。

---

## 2. 架构：无头引擎 + 可换 UI

| 维度 | 事实 |
|---|---|
| 进程边界 | 引擎与 UI 严格分离；UI 不持有持久化规则 |
| 单一真相 | Engine 拥有数据、装配、Agent 执行、安全边界 |
| UI 角色 | 可换壳；WebUI 当前主面，桌面端保留维护线 |
| 协议层 | 共享线协议 + Envelope/WidgetDef 等传输无关类型 |

**理念含义**：解耦是“内核数据面 + 任意壳”，天然支持未来换 UI / 远程 / 多端，而非把一切压在前端进程内。

---

## 3. 数据模型与 Schema 立场

- **角色/世界书载体**：标准 JSON——角色卡 `card.json`（V2 卡规范）、世界书 `lorebook.json`。
- **Schema 位置**：独立、规范化、版本化的**合同**（如 Worldbook v4 schema），经 `normalize_worldbook` 统一。
- **数据与叙事分离方式**：JSON 内结构化字段（`keys`/`enabled`/`priority`/`constant`）vs `content` 文本（可为 markdown）；**不是**文件格式层面的分离。
- **第三方兼容**：normalizer 显式吸收 SillyTavern 别名（`key`→`keys`、`disable`→`enabled`、`order`→`priority` 等），但独立实现不复制代码；`extensions` 保留 ST-only 字段供未来使用。

**与“文档不需要 schema”立场的对照**：本项目大量且显式使用 schema（版本化合同 + normalizer + sha256 manifest），与“文档不需要 schema”相反。

**与“数据用 JSON 省 token”立场的对照**：本项目角色卡/世界书均为 JSON，结构化字段与 content 分离，与该立场一致。

---

## 4. 控制面与 RP 数据分离

- 原则：“RP 角色 prompt 只包含 RP 数据；工具、调度、审计留在结构化控制平面。”
- 路由/槽位由**引擎**决定：世界书注入固定在 RP system-prompt 的 `[World Info/Lorebook Information]` 区块；角色卡数据进引擎定义的固定装配槽位。
- 作者自由度：低但受界——数据进固定槽位，Agent loop 有界（30 内置工具），不鼓励在 prompt 路径塞脚本。
- `UI-PROTOCOL-DECISION` 硬规则：**Agent 不得在运行时写 Vue/JavaScript/任意前端代码**；Widget 只渲染 Blueprint、发 intent，不持有 RP 数据真相。

**与“直接把文档丢给 AI”立场的对照**：本项目由引擎按固定槽位装配 JSON 数据，而非原样透传文档。

**与“角色卡内容如何进入预设槽位”立场的对照**：本项目答案是**引擎固定装配槽位**；对照的 G 项目答案是**作者自定义路由（容器 + role 标签）**。二者都解决了“让用户自己选容器”的甩锅，只是决定权归属不同。

---

## 5. 增量读取与 Token 策略

| 维度 | 事实 |
|---|---|
| 记忆/状态层 | 当前以**版本化**为主：每条消息绑定 `content_revision`，不可变快照可重放 |
| 文档层 | 装配前整体校验选定 revision 的不可变快照；无“文档增量编译”概念 |
| 长会话处理 | PLAN 列为 **P2** 未来项（“长会话窗口化/虚拟化与资源上界”），尚未实现 |
| 核心机制 | 内容寻址（sha256 tree hash）+ revision 快照 + 崩溃恢复 |

**与“只靠 diff 做增量读取”立场的对照**：本项目不靠 diff markdown，而是靠**结构化状态版本 + 上层缓存/快照**实现增量（可复现），与“只靠 diff 做不到增量读取”的判断一致。差异在于：本项目的增量叙事偏“可复现/可回滚”而非“省 token”，压缩摘要是明确推迟到 P2 的未实现项；G 项目则在记忆层已设计分级压缩摘要以省 token。

---

## 6. 完整性与恢复（显著强项）

`SESSION-DATA-DESIGN.md` 定义了极严格的合同：

- 统一 `content_revision`；session 自包含、工作副本物化、revision 不可变快照。
- `AIRP-TREE-SHA256-v1` 算法（规范化路径 + 逐文件 sha256 + 树 hash）；加载前全量校验，禁止回退可变副本。
- JSONL torn-tail 崩溃恢复：同步边界、损坏行保留不静默删、修复前复制原始记录。
- 派生角色卡、复制开局、提升默认均为显式审计操作。

**理念含义**：把“可审计、可恢复、用户资产主权”当作首要产品目标并前置到 P1；而非把开放性/扩展性前置。

---

## 7. 治理与未来发展哲学

| 维度 | 事实 |
|---|---|
| 发展节奏 | **P1 收敛**：功能面超过验证面即冻结新子系统扩张 |
| 质量门禁 | **审计 bot 为合并阻塞门禁**；独立审计三原则（不附和、可提己见、可质疑历史） |
| 第三方态度 | 只吸收理念，独立实现，不复制第三方代码/prompt/测试/资产 |
| 重构哲学 | **代际重构特例**：每半年/年可显式推倒重建（remake 分支），但须市场验证后才替代，且不破坏用户资产 |
| 扩展准入 | 新扩展须有真实用户工作流、不绕过 P1 正确性/恢复/安全门、沿 `service→HTTP→WebUI→test` 纵向闭环 |
| 证据分层 | 单元/route/browser/artifact/production/人工/市场证据各自只证明自身覆盖面 |

**理念含义**：稳健优先——先把正确性、可恢复、可审计、资产主权做扎实，再扩张功能。

---

## 8. 桌面旗舰 UI 现状（关键发现）

桌面端（`ui/`，Tauri/Vue）原计划是“长期旗舰产品交付面”，承载最丰富的扩展愿景：

- Widget/Slot 扩展点注册表（第三方 Widget 挂载命名位置）；
- 第三方 Widget 本地导入→原生运行（consent、生命周期、provenance SHA-256）；
- AI 驱动 Widget 生成（L1 声明式 / L2 模板实例化 / L3 代码生成，分级闸门）；
- Theme Pack / Layout Profile / 命令注册表；
- 酒馆兼容“两手策略”（声明式第三方兼容模式 + 原生 AI 生成）。

**但该计划已归档暂停**（`docs/archive/2026-07-29-desktop-ui-canvas-relay-plan.md`），且核心想法**未落到引擎运行时**：

- 计划书自承 `ui/src` **不存在** slot 注册表——widget 只能整体替换区域；
- 沙箱端到端加载“**从未运行时验证**”；
- 第三方 Widget 导入、AI 生成 L1 渲染器、酒馆兼容 shim 全排在 R5 棒次（随暂停未推进）；
- 引擎合同层仅“消费 webui 成熟的 HTTP/SSE 合同”，自定义数据 schema v1 + migration 属计划、未指已合入引擎。

**理念含义**：最“炫”的扩展想法目前停留在纸面，且 `UI-PROTOCOL-DECISION` 明确把“通用 Agent UI 标准/协议优先平台/第三方 widget 市场”**降级**为未来可能性，核心资产仍是 RP Agent 引擎与产品闭环。即便旗舰 UI 未来交付，其扩展也只触及**界面层**（widget/slot/主题），**触不到 prompt 装配路径**——这恰是本项目主动拒绝“让作者/agent 在运行时改写结构”的哲学体现。

## 9. 与 G 项目的理念分叉（匿名对比）

G 项目特征（事实，不点名）：通用 LLM 前端；TS/Vue/Tauri；自定义混合文档格式 IMD（markdown 叙事 + JSON 数据 + role 模板 + JS 宏）；插件作者用 `containers` + 引用 + `agentprocess/index.js` + `codeAct`（让模型执行 JS）自定义结构；设计先行、功能快速铺开。

| 维度 | 本项目（AIRP） | G 项目 |
|---|---|---|
| 定位 | RP 特化 Agent 客户端 | 通用 LLM 前端 |
| 运行时 | Rust 无头引擎 + 可换 UI | 前端进程内直接调本地库 |
| 数据格式 | 标准 JSON（card.json / lorebook.json） | 自定义混合文档（markdown + json + role + JS 宏） |
| Schema 立场 | 版本化合同 + normalizer + sha256 manifest | 文档内块结构 + 编译期校验 |
| 路由决定权 | **引擎**（固定装配槽位） | **作者**（容器 + role 自定义） |
| 增量机制 | 版本化快照可重放；压缩省 token 推迟到 P2 | 记忆层分级压缩摘要（已设计） |
| 完整性/恢复 | sha256 + torn-tail + revision（强） | 依赖本地库 + 状态版本设计，文档层全量重编译 |
| 治理 | 审计 bot 阻塞合并 + 代际重构 + 证据分层 | 设计文档详尽，无强制审计门禁 |
| 作者结构自由 | 低（引擎锁死装配，UI 扩展不触 prompt） | 高（可重定义容器、跑 JS） |
| 折腾门槛 | 高（Rust 引擎重编 + 过审计） | 低（前端改文件即看效果） |

**根本分歧**：不在“要不要 schema”（两者都用显式 schema），而在**结构权归谁**（引擎 vs 作者）与**先把什么做扎实**（可恢复性 vs 开放性）。

**关于“把旗舰 UI 纳入考量”**：即便计入已归档的桌面旗舰 UI 计划，它扩展的也只是**界面层**（widget/slot/主题），且本项目在 `UI-PROTOCOL-DECISION` 中主动拒绝“让作者/agent 在运行时改写结构/前端代码”。因此 G 项目独有的是 **prompt 装配层的作者自由**与**非 RP 通用性**——这两点不被旗舰 UI 抹除；而旗舰 UI 自身仍停在归档文档，G 项目的对应能力已落地。

---

## 10. 结论

- 本项目是一个**理念清晰、治理严格、面向可恢复性的 RP Agent 内核**：无头引擎解耦、JSON 规范化 + 版本化合同、sha256 完整性、审计门禁、代际重构余地。
- 其扩展性与兼容性（normalizer 吸收第三方别名、标准 JSON、有界 Agent loop + webhook/脚本插件）是**真实的、引擎侧的**。
- 其最“炫”的 UI 扩展愿景（widget/slot/AI 生成/酒馆兼容）**集中在已归档暂停的桌面旗舰 UI 计划**，未落地引擎，且即便交付也只触及界面层、不触 prompt 装配。
- 与 G 项目的分叉是哲学性的：本项目收结构权于引擎、先求可信；G 项目放结构权于作者、先求开放。两者都反驳“文档不需要 schema / 直接透传文档”，都印证“数据/叙事分离”与“增量不能只靠 diff”。
- 若优先考虑**可恢复性、资产主权、审计可追溯**，本项目更合适；若优先考虑**作者结构自由、非 RP 通用性、低折腾门槛**，G 项目更合适。本报告不就“谁更优”做整体裁决。

（本报告仅陈述事实与理念分析，未对任一项目做可用性评判，亦未点名对照项目。）

### A.2 G 项目 记忆系统架构（源码核对）
双通道 + 三层模型：

- **T1 权威静态定义层**：角色卡 / 世界书，永不压缩，单一真相源。
- **T2 无损可变状态层（条目式记忆）**：作者预先声明的固定 schema 变量，确定性沙箱 JS 沿消息流重放维护。`InteractiveVariableDefinition`（name/description/initialValue/wrapperSource）；`applyVariableUpdate` 在 Proxy 沙箱执行 `source`，禁 Math.random / Date.now / Promise / IO。
- **T3 派生召回缓存层（压缩式记忆）**：递归段树 LLM 压缩。`summarizeContainerRange`/`summarizeSegmentRange` 把旧消息区间摘要成 level-1，再 4 合 1 递归；内容寻址（sourceHash），`validSegmentsForPath` 按激活路径增量自愈。`selectMemoryFrontier` 未压缩段回退 `containerToModelMessages` 直取原文。**设计文档第 634 行明写"不删除原始消息"**——即原文留库，上下文里旧内容用摘要表示。

AIRP 对应物：
- T1：角色卡 / 世界书（同，保真）。
- T2 雏形：`resident.md`（**有损** LLM 压缩 2000 字缓冲，非无损变量）——这是二者事实轴差异点。
- T3：分卷系统（`current.md` 原文 + `index.md` 结构化头部 + 封存卷），Aho-Corasick 关键词召回；另建 FTS5 全量历史检索（**已建未接入提示词注入**）。

### A.3 原报告 §5/§9 的两处修正
1. **"AIRP 压缩推迟到 P2 未实现"已过时**：`finalize.rs` 的 `run_memory_extraction` 已是 `extract_facts → commit_extracted_facts → apply_decay_to_resident → compress_resident_memory` 完整链路，压缩已落地。原报告审计时点（网页端阅览，未下源码）未能看到此实现。
2. **"G 项目 分级压缩摘要"并非无损优势**：设计文档第 38 行自认"压缩摘要是原始消息区间的**有损**派生结果"；其优势是段树全覆盖 + 优雅降级（每轮都有某层摘要覆盖），劣势是深层摘要失真复利累积。原报告低估了这种失真。

### A.4 遗忘曲线：极端条件（1M 上下文窗口）对比
两类遗忘必须区分：
- **破坏性遗忘**（存储丢失）：压缩摘要一旦生成，原区间在"召回视图"中被不可逆替换为摘要 → 精度衰减到 0。G 项目 T3 深层摘要、AIRP `resident.md` 均属此类。
- **非破坏性遗忘**（存储保留、召回门控）：AIRP 分卷正文逐字留盘，仅当关键词未在 `index.md` 命中时不注入 → 有低位地板（faithful 存储始终在），非零。

| 机制 | 极端长会话下 | 地板 |
|---|---|---|
| G 项目 T3 压缩摘要 | 旧消息递归合并，细节逐步丢失 | 趋近 0（破坏性） |
| AIRP resident.md | 同破坏性压缩 | 趋近 0（破坏性） |
| AIRP 分卷（正文） | 正文恒在，仅召回门控 | 非零（非破坏性） |

结论：在"叙事历史代表性保真"轴上，AIRP 分卷逐字留盘 ≥ G 项目 有损 T3；G 项目 的优势在覆盖完整性（每轮都有摘要），AIRP 的弱点在关键词召回门控（未命中则整轮不召回）。

### A.5 "无损确定性变量"的定义与几何爆炸边界
- **定义**：变量是**作者预先声明**的固定 schema（`InteractiveVariableDefinition[]`），状态为固定形状 `Record<string, InteractiveValue>`。**不是** agent 自动识别、每个抉择自动成变量；模型只在已声明 schema 上输出确定性更新函数。
- **增长模型**：
  - 标量字段：状态对象大小 O(声明字段数)，与抉择数**无关**。
  - 更新函数日志：O(回合数) 线性可重放（§3.17：1 万条已编译函数执行 ≈ 3ms）。
  - **集合值变量**（时间线 / 事实列表 / 关系表）：其值随剧情**线性累积，无自动上限** → 这才是真正会"几何爆炸"的地方。
- **对早前论断的修正**：早前称"G 项目 条目式无损优于 AIRP resident.md"需加限定——
  - (a) 无损仅覆盖**作者预建模的极少数字段**，绝大多数叙事细节不进变量系统（进有损压缩摘要），范围很窄；
  - (b) 集合值变量无损 = 无界增长，靠作者 schema 自律；AIRP 2000 字压缩是**自动上限**的务实取舍。
  - 二者是"有界 + 模糊" vs "无界 + 精确（仅声明字段）"的取舍，非单纯谁优。
- **角色卡全部设定都不符合"作者点名字段"怎么办**：答案在三层层模型——T1 静态权威层**完整持有角色卡原文**（永不压缩，单一真相），T2 只承载少量需精确可变的点名字段，T3 承载派生召回。即"全设定"始终在 T1 保真，"点名字段"只是 T2 的窄子集；未被点名的设定不会丢失，只是不进入结构化可变状态。切勿把整个角色卡塞进 T2。

### A.6 固定 schema 变量的语义落地缺口（灵石 = 金钱）
- 场景：作者只声明字段 `money`，剧情用"灵石"= 金钱。Agent 如何把"灵石 −10"写进 `money`？
- **源码确认**：`interactive-document.ts` **无别名 / 同义词表**（仅有 `resolveReference` 解析文档内 `{{ref}}`）；`applyVariableUpdate` 直接跑 `source` 操作 `state.money`。变量层无任何别名 / 本体归约。
- 落地只能靠：(a) 作者在变量 `description` 写明同义词；(b) LLM 写更新时临场脑补映射。两者皆**非确定性、brittle**；schema 枚举不出每个世界的同义词。
- **关键区分**：G 项目 的"确定性"是**更新内**的（给定 `source` 重放精确），**非更新间**的（哪个表面词 → 哪个字段，由 LLM 每次非确定性决定）。所以"无损"描述**执行**，不描述**语义归约**。
- **AIRP 在此子问题反而更对**：世界书 `lorebook.json` 的 `keys`（触发同义词）+ 分卷索引 `(别名: ...)`（`parse_entity_line` 解析）已是**确定性别名原语**，只是用在检索 / 实体层，未接到结构化写入。健壮解法是独立别名 / 本体层同时驱动检索与写入归约，而非让 LLM 每次猜。

### A.7 隐式落地（约定俗成 / 训练先验）常已足够——修正"显式别名更优"的倾向
- 用户论点：人读"灵石"自然带入 = 金钱（约定俗成 / 第一印象）；作者惯性不点明；LLM 训练材料含同类内容 → 上下文不必强调也能带入功能。即**隐式语用推理 + 预训练先验**。
- **成立处**：常见套路（灵石 = 货币）下隐式落地足够；强制显式别名是过度工程 + 增作者负担 + 逆人性。
- **真实失效边界**：(a) 非确定性 → **长会话漂移**（state.money vs state.lingshi 孤儿字段跨千轮累积）；(b) 颠覆 / 自定义世界套路误导；(c) 易混表面词（灵石 / 灵币 / 灵玉）；(d) 换小模型丢失套路先验。
- **合成**：非"谁对"，是**谱 / 风险权衡**。默认隐式（零成本，套路够用）；显式别名作**可选、廉价安全网**，只在风险边界（自定义世界、长会话一致性、换模型、精确查询）启用，主要为保**跨轮一致性**而非单次正确。
- **修正早前"统一本体层"建议**：AIRP 世界书 `keys` 本就 opt-in（想建才建），默认正确；勿把别名变强制 schema，保留 opt-in 性质。

### A.8 终局场景：饭后留一枚灵石在桌上便离开（全程不提"交易 / 买卖"）
- 原文："我吃完饭，将一枚灵石放在桌子上，便离开了。"
- **G 项目 T3（压缩记忆）= 存得住，但有损**：原文消息照进对话日志；`summarizeContainerRange` 只产派生摘要、不删原文；`selectMemoryFrontier` 未压缩段回退直取原文。事件先被忠实存储，长会话中被递归摘要吞掉精度（"一枚灵石放桌上" → "桌上留了东西"），且 frontier **自动注入**提示词。故"无法存记忆"对 T3 言过其实。
- **G 项目 T2（条目式变量）= 真盲**：作者只声明 `money`；场景无交易动词、无赋予 / 支付动作 → `state.money` 无 delta → 不写任何变量。`resolveReference` 无别名表，"灵石"也不归约到 money，且本就无赋值事件。用户"无解"断言在此**成立**。
- **两系统共有真缺口（非 G 项目 独有）**：隐性叙事意义落地。桌上留石可能是线索 / 付费 / 仪式 / 伏笔 / 垃圾；无作者建模（如 `left_items`）或 LLM 推理，任何结构化层都不捕"此石有意义 / 何义"。这正是整条 thread 归宿：结构化变量记忆本质上捕不到隐性、非交易叙事事件。
- **AIRP 同场景**：`resident.md` 有损压缩（同 G 项目 T3 退化风险）；分卷若索引实体含"灵石 / 桌"则逐字留盘（保真优于 G 项目 有损 T3），但关键词门控召回 + FTS5 已建未接入注入 → 存得住却可能取不回。
- **判决**：用户"G 项目 无法存此记忆"对 T3 言过其实、对 T2 准确；深层论点（固定 schema 变量对隐性非交易事件结构性失明）成立且非 G 项目 bug。勿因此羡慕其变量层；AIRP 应补的是把 FTS5 接进 `prepare.rs` 注入（消除"存得好取不回"），而非引入变量系统。

### A.9 整体结论（对本报告 §9 / §10 的修正与补全）
- 原报告隐含的"本项目记忆 / 分卷不如 G 项目"判断被**证伪 / 收窄**：该判断建立在"G 项目 压缩无损领先 + AIRP 压缩未实现"两个过时 / 失真前提上，二者均不成立。
- **净结论（替换原 §9 末句的单轴优劣暗示）**：非"谁更优"，而是各自优化不同轴——
  - AIRP 强在**存储保真 + 可恢复性**（sha256 / revision / torn-tail / 原子写 / 分卷逐字留盘）；
  - G 项目 强在**结构化事实无损 + 覆盖完整性**（条目式变量 + 段树全覆盖）；
  - 二者当前**都无语义入上下文检索**（G 项目 列为未来阶段；AIRP FTS 已建未接注入）。
- **AIRP 应闭合的真实短板（非"引入压缩"或"引入变量系统"）**：
  1. 把有损 `resident.md` 事实缓冲换成**少量固定 schema 无损状态通道**，只承载必须精确的东西（血量 / 关系布尔等），绝不令事实自动成变量（防集合值无界膨胀）；
  2. 修关键词召回门控：把 FTS5 / 下探检索接进 `prepare.rs`，消除"存得好却取不回"；
  3. 可选：用递归段树层次替换扁平卷索引做优雅多级覆盖，但**保留正文逐字**（勿删原文，与 G 项目 一致）。
- 本报告原 §0–§10 正文及匿名表述保持不变；本附录仅补充后续源码审计结论。
