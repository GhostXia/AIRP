## 2. 核心裁决：奇美拉战略是死路

### 2.1 字面问题——"奇美拉"就是病灶本身

"奇美拉"字面即缝合怪。PR #458 §0 摘要里"用 X 的 A + Y 的 B + Z 的 C + AIRP 自有 D"的句式，是 RP 赛道失败项目坟场里最常见的句式。原因不是"缝合不优雅"，而是：

- **每借一个功能，就借来一份维护债**。ST V2/V3 角色卡兼容、Talemate 时间系统 UI、Marinara 多站浏览器、Agnai 群聊调度——每一项在原项目里都是多年的有机演化，移植过来是无根的。
- **每个功能在原项目里有支撑结构，移植后失去**。Talemate 的导演 Agent 好用，是因为它背后有 ChromaDB 长期记忆 + 分层历史压缩 + Jinja2 模板 + per-Agent API 选择共同支撑。只抄导演，抄来的是空壳。
- **奇美拉战略合法化范围膨胀**。[CURRENT-BASELINE.md](../CURRENT-BASELINE.md) §2.1 与 [RISK-REGISTER.md](../RISK-REGISTER.md) 多次记录的"功能面超过验证面"病灶，正是奇美拉战略的必然产物。

PR #458 §5.1 A1 已识别此点，但仅建议"补 NOT 吸收清单"。**这是软处理**——NOT 清单只能砍掉边缘项（UNO/Chess/Spotify DJ），不能解决"核心缝合本身不可行"。如果奇美拉是死路，NOT 清单只是给死路刷漆。

### 2.2 五家先行者的逐项对照——AIRP 没有独占卖点

把 PR #458 §2 与 §3 的"差异化"逐项核验，结果是 AIRP 声称的每个卖点都有更早的先行者：

| AIRP 卖点（PR #458 §3 / [PLAN.md](../PLAN.md) §1） | 已有先行者 | 先行者优势 |
|---|---|---|
| 导演 Agent | Talemate | 多年迭代 + 逐项行动开关 |
| 世界时钟 / 时间流逝 | Talemate | 场景视图可编辑时间条目 |
| 无头 Engine + 前端分离 | Waidrin（p-e-w） | 明确宣称可驱动任何前端 |
| 多 Agent 编排 | Talemate、astrsk | 后者做成可视化 Flow |
| Agent 原生运行时哲学 | fount（steve02081504） | 哲学更激进，社区已成型 |
| 长期记忆 / 遗忘 | Talemate | ChromaDB + 分层压缩 |
| 酒馆生态兼容 | 全行业标配 | ST/RisuAI/Agnai 全部支持 |
| 治理 + 原子提交做护城河 | 无直接先行者 | 但非用户可感知——见 §4 |

**硬结论**：AIRP 目前没有一个卖点是独占的。它不是在空白赛道里定标准，而是在一个至少有四个先行者的赛道里做后发者。后发者靠缝合永远追不上——因为先行者的功能是有机的、有真实反馈校准的，AIRP 抄过来的是无根的、由开发 agent 自审的。

PR #458 §5.3 C1 已识别"护城河 claim 可疑"，但只建议"重新审视护城河定位"。**这也太软**——C1 追到底就是"治理 + 原子提交是工程基线（must-have），不是护城河（differentiator）"，而如果把它降级为基线，AIRP 就没有任何独占卖点了。

### 2.3 PR #458 §5 自审计的不足

| PR #458 §5 疑点 | 本审计评价 | 本审计追加结论 |
|---|---|---|
| A1 奇美拉陷阱 | 识别正确，但 NOT 清单救不了 | 战略本身不成立，需重定位（§5） |
| A2 P0 排序与 0.0.3 脱钩 | 识别正确 | 不止脱钩，是**战略级逃避**——在 #130 没通过前谈 0.0.4+ 战略，等于用未来承诺转移当前阻塞的注意力 |
| A3 per-agent 与 token 可视化耦合 | 识别正确 | 同意，不追加 |
| B1 多用户架构预留 | 识别正确但保守 | 多用户是真正能改变赛道形态的差异化点之一（见 §5.2），不应只标 P2 预留 |
| B2 Game Mode P3 关闭战略门 | 识别正确 | 同意 |
| B3 模型策略缺位 | 识别正确 | 同意，但补"模型策略"不解决奇美拉根本问题 |
| C1 护城河 claim 可疑 | 识别正确，结论太软 | 追到底：护城河不存在，需重定位 |
| C2 竞品清单不全 | 识别正确 | 同意，但补闭源竞品研究不改变"无独占卖点"结论 |
| D1 代际重构衔接 | 识别正确 | 同意 |
| D2 第三方独立性 | 识别正确 | 同意 |

**总结**：PR #458 §5 识别的问题都对，但每条都停在"补清单/补研究/重新审视"层面，没有一条追到"战略本身不成立"。这是自审计的天然局限——审计 agent 审计自己刚写的文档时，倾向于给自己留台阶。本审计作为对位再审计，没有这个包袱。

## 3. "找缺口做开放规范"也是变种奇美拉

PR #458 §5 没提这点。但本审计认为这是最常见的下一层陷阱，必须显式否定。

**典型陷阱句式**："五家都没做到'酒馆生态完全兼容 + Agent 编排语义开放规范化'，这才是 AIRP 该赌的独占点。"

### 3.1 用户视角 vs 开发者视角的缺口错位

RP 用户不会说"我想要一个开放规范化的编排语义"。他们说："角色老是忘事"、"剧情推不动"、"AI 一直在重复"、"我不知道它为什么这么写"。

把"编排语义开成规范"当成独占点，等于把项目重定位成给前端开发者用的中间件。RP 赛道的前端开发者是极小众——绝大多数用户是终端用户，不会改 prompt、不会写插件、不会读规范。

### 3.2 没有采用者的规范是空规范

谁会去实现 AIRP 的编排规范？

- **SillyTavern**：有自己的脚本钩子 + ST 扩展生态，没理由实现第三方规范。
- **Talemate**：封闭自家格式，开放规范等于自废武功。
- **Waidrin / fount / astrsk**：与 AIRP 是直接竞品，没理由替竞品背书。
- **新前端**：LSP 能成是因为背后有 VS Code 的分发撑着；MCP 能成是因为背后有 Claude 的分发撑着。AIRP 背后有什么？

AIRP 0.0.3 还没到真实用户手里，分发为零。一个没有采用者的规范，只是项目在自说自话。

### 3.3 "开放规范"是缝合抽象的变种

奇美拉战略 v1 是缝合功能；"找缺口做开放规范"是缝合抽象。两者同构：

- 缝合功能：吸收五家的好功能 → 维护债爆炸 → 平庸。
- 缝合抽象：吸收五家的好理念提炼成规范 → 没人实现 → 空谈。

**变种奇美拉仍然是奇美拉**。PR #458 §5 没识别这一层，本审计显式否定它。

## 4. 真正的护城河缺口：分发

PR #458 §2 列了竞品但没分析"为什么 Talemate 技术上多个维度超过 SillyTavern、用户量却只有 SillyTavern 的零头"。这是赛道地图里最该让 AIRP 警觉的事实。

### 4.1 SillyTavern 的护城河不是代码

SillyTavern 的真正护城河是：

- **janitor.ai / chub.ai / character-tavern 的卡片分发**——用户去卡片所在的地方。
- **几年的插件 / 正则 / 预设社区沉淀**——这些是真实用户在使用中产出的，不是开发 agent 一次性写的。
- **用户迁移成本**——自己的角色卡、世界书、预设全部绑死在 ST 格式上。

### 4.2 兼容只能是单向管道

AIRP 的"酒馆兼容"如果只是导入导出，等于免费给 SillyTavern 做迁移工具——用户能从 ST 进 AIRP，但没人在 AIRP 这边产出新卡。

Talemate、RisuAI 都做兼容，都没靠兼容抢到用户。原因：兼容只能让你"读得到"ST 卡，不能让你"值得留下"——留下需要原生内容生态，而原生内容生态需要用户基数，用户基数需要分发渠道。这是先有鸡先有蛋问题，AIRP 0.0.3 没有解。

### 4.3 反馈循环差距会复利

更刺眼的是时间维度。AIRP 0.0.3 还在为 #130 maintainer 验收挣扎——真实 provider onboarding + production Compose + real browser smoke。这四个对手已经在用真实用户反馈迭代多年。

这不是功能差距，是**反馈循环差距**，而反馈循环差距会复利：

- 每过一个月，Talemate 收到的真实世界反馈比 AIRP 多一个数量级。
- 它的迭代方向就比 AIRP 准一个数量级。
- 功能可以追，复利的反馈差距追不上。

PR #458 §4 的 P0–P3 优先级表里没有任何一项解决反馈循环差距。**这是奇美拉战略最深的盲点**——它假设 AIRP 有时间慢慢吸收五家优点，但实际是每过一个月，要追的距离就大一截。

## 5. 战略重定位提案

不是奇美拉，也不是"找缺口做规范独占"。是三选一，每条带代价。本审计不预设哪个对——选择属于用户人工 review 决策，不属于审计 agent。

### 5.1 选项 A：开放数据，不是开放规范

把世界状态、Agent 决策轨迹、记忆压缩过程全部以可读、可导出、可外部消费的形式开放。让用户能真正拿走自己的 RP 数据、审计 AI 为什么这么写、迁移到任何地方。

- **打痛点**：Talemate 封闭 + fount 哲学小众两个痛点。
- **代价**：放弃锁定用户的能力——用户能走，所以必须让他们想留。
- **可证伪条件**：如果用户拿到可读导出后还是不导出、不审计、不迁移，说明这个能力不是用户感知点，选项 A 失败。
- **与既有规则衔接**：与 [PLAN.md](../PLAN.md) §1 "用户资产必须可迁移、验证、导出和回滚" 一致；与 [CURRENT-BASELINE.md](../CURRENT-BASELINE.md) §3 "用户资产优先" 不变式一致；与 #346 完整 migration / 导出闭环同向。

### 5.2 选项 B：Agent 可解释性给玩家，不是给开发者

每个 AI 回复附带"它为什么这么说"的轻量追溯：用了哪些世界书条目、记忆压缩到了什么、导演干预了哪一步、消耗了多少 token。

- **打痛点**：直接打 RP 玩家最痛的"AI 在乱编"问题。Talemate 的 Agent 活动栈是给用户看 Agent 在忙什么，但没解释"这条回复为什么是这样"。
- **代价**：prompt 预算和性能——每条回复附带可解释性 metadata 会增加 token 成本和延迟。
- **可证伪条件**：如果用户在 A/B 测试里不倾向于选择带可解释性的版本（即使更慢更贵），选项 B 失败。
- **与既有规则衔接**：与 [AGENT-ORCHESTRATION.md](../AGENT-ORCHESTRATION.md) 的"有界 Agent + 可观察事件" 一致；与 PR #458 §5.2 B3 "模型策略缺位" 部分呼应（per-Agent 决策的可观察化是模型策略的前置）。

### 5.3 选项 C：承认 AIRP 的最佳想法可能不该以独立仓库存在

如果 AIRP 的导演 Agent 真的比 Talemate 好，去 Talemate 做 PR；如果编排可视化真的有价值，去 astrsk 做；如果 Agent 可解释性是真的差异化，去 SillyTavern 的扩展生态做。

**项目的价值不等于仓库的存在**。维护者的时间是稀缺资源，投入到哪里产出最高，哪里就是正确选择。

- **打痛点**：直接打反馈循环差距——把 AIRP 的好想法嫁接到有真实用户的项目里，立刻获得反馈循环。
- **代价**：最痛——等于承认 AIRP 作为独立仓库可能不是最优载体。但审计章程第三条最硬核的应用就是这条：不把"前人已定"当不可质疑前提，包括"项目必须以独立仓库存在"这个隐含前提。
- **可证伪条件**：如果上游项目拒绝接受 AIRP 的好想法（许可证、社区规则、技术方向不兼容），且拒绝是结构性的而非一次性的，选项 C 失败，回退到 A 或 B。
- **与既有规则衔接**：与 [AGENTS.md](../../AGENTS.md) "第三方经验吸收与独立实现"（2026-07-11）反向对偶——AIRP 既可以吸收第三方理念，也可以反向把自己的理念贡献给第三方。该规则禁止复制第三方代码，但**不禁止** AIRP 把自己的代码以独立实现的形式贡献给第三方（前提：保留 AIRP 自己的许可证选择，且不要求第三方按 AIRP 边界收下）。
- **与代际重构特例的关系**：选项 C 不是代际重构，不需要启动 §代际特例流程；它甚至比重构更激进，因为它在仓库层面做减法。

### 5.4 三选项的共同前提

不管选哪条，前提都是先承认两点：

1. **奇美拉死路成立**——PR #458 §5 A1 识别正确。
2. **"找缺口做开放规范"是变种奇美拉**——本审计 §3 的硬结论。

如果这两点中任何一点被推翻（见 §7），三选项的前提就塌了，需要重新战略定位。

### 5.5 三选项不互斥，但有优先级

- A 与 B 可同时做——开放数据和 Agent 可解释性是同一类透明性方向。
- C 与 A/B 互斥——C 是放弃独立仓库，A/B 是保留独立仓库但重定位。
- 本审计**倾向 A + B 组合**，因为它们的代价是工程性的（性能、token），而 C 的代价是项目层面的（仓库存在性）。但这是审计 agent 的倾向，不是裁决。

## 6. 自指审计：本文件自身可能错在哪里

按 AGENTS.md "审计 Agent 守则" 第三条——agent 的智能是不断迭代增强的，曾经审计此仓的 agent 的能力和眼界可能远不如现在你这一代。本审计自身也接受被下一代审计 agent 质疑。预先列出本审计可能的错误：

### 6.1 "用户不想要开放规范"是基于推断，不是证据

本审计 §3.1 断言"RP 用户不会说'我想要一个开放规范化的编排语义'"。这是基于对 RP 用户群体的常识推断，**不是基于 AIRP 真实用户的证据**——AIRP 0.0.3 还没有真实用户。

**可能的错误**：RP 用户群体里可能存在一个被忽视的"高级用户 + 业余开发者"子群体，他们确实需要开放规范来定制工作流。SillyTavern 的扩展生态存在这个子群体，AIRP 可能也有。

**翻盘条件**：出现具体的、可复现的高级用户工作流需求，且开放规范是其唯一解。

### 6.2 "分发是真正护城河"可能在小众赛道里不成立

本审计 §4 断言"真正的护城河是分发"。这是基于 SillyTavern vs Talemate 的对照，但 Talemate 用户量低可能有其他原因（产品哲学、UI 门槛、社区运营），不一定是分发问题。

**可能的错误**：在 RP 这个相对小众的赛道里，可能存在"小而精 + 高留存"的子模式，靠产品差异化而非分发取胜。fount 哲学激进但小众却仍存活，可能是反例。

**翻盘条件**：出现一个无分发优势但靠产品差异化在 RP 赛道长期存活且用户量增长的具体案例。

### 6.3 "考虑上游贡献"可能被读成自我否定

本审计 §5.3 选项 C 是最容易被误读的一条。"承认 AIRP 的最佳想法可能不该以独立仓库存在"可能被读成"建议放弃 AIRP"，这会打击维护者士气和社区信心。

**可能的错误**：选项 C 的真实意图是"投入产出比"判断，不是项目价值判断。但如果维护者读到的不是"投入产出比"而是"你做的不重要"，本审计就是有害的。

**翻盘条件**：如果维护者明确表示选项 C 的表述方式不可接受，本审计应撤回 §5.3，重写为更精确的"投入产出比"语言，或彻底删除。

### 6.4 本审计自身也犯了"开发者视角"的错

本审计 §3.1 批评"开放规范是开发者视角的缺口"。但本审计 §5 提出的三个选项（开放数据 / Agent 可解释性 / 上游贡献）也大量使用开发者视角的概念（数据 schema、可观察性 metadata、PR 贡献）。

**可能的错误**：本审计没有真正从 RP 终端用户视角提出选项。真正的用户视角选项可能是"装了就能玩 + 角色不胡说 + 剧情不卡住"这种朴素体验目标，而本审计 §5 没提任何一条这种朴素选项。

**翻盘条件**：如果出现 0.0.3 #130 通过后的真实用户反馈，且反馈指向的痛点与本审计 §5 三个选项都不对应，本审计 §5 应被推翻重写。

### 6.5 本审计对 PR #458 §5 的批评可能过苛

本审计 §2.3 批评 PR #458 §5 "结论太软、没追到硬终点"。但 PR #458 §5 是**自审计**——审计 agent 审计自己刚写的文档时，天然会留台阶。这是制度性问题，不是 agent 能力问题。

**可能的错误**：本审计作为对位再审计，没有自审计的制度约束，天然可以更激进。但这不意味着本审计的激进结论更对——可能只是制度位置不同。

**翻盘条件**：如果后续审计 agent 认为本审计 §2.3 的批评是对自审计制度的不当否定，本节应撤回。

## 7. 什么证据会让本审计翻盘

本审计欢迎被再审计。以下证据出现时，本审计的对应结论应被推翻：

| 翻盘证据 | 影响的结论 | 翻盘后的处理 |
|---|---|---|
| 0.0.3 #130 通过后，真实用户反馈明确指向"想要开放编排规范" | §3 整节、§5 选项前提 | 撤回 §3，重审"开放规范"是否真是用户需求 |
| 第三方前端明确承诺实现 AIRP 编排规范（书面、有截止日期） | §3.2 "没有采用者的规范是空规范" | 撤回 §3.2，开放规范路线恢复可行性 |

| 出现"无分发优势但靠产品差异化在 RP 赛道长期存活且用户量增长"的具体案例 | §4 "分发是真正护城河" | 撤回 §4，分发不是唯一护城河，奇美拉战略可能局部成立 |
| 维护者明确表示 §5.3 选项 C 表述方式不可接受 | §5.3 选项 C | 撤回 §5.3 或重写为更精确语言 |
| 后续审计 agent 给出本审计未考虑的、用户视角的战略选项 | §5 整节 | 撤回 §5 全部三选项，重写 |

**所有翻盘证据目前均不存在**。这是本审计结论成立的边界条件。一旦任一证据出现，对应结论应被重新审计。
