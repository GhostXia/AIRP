# PR #601 independent audit

Date: 2026-08-26  
Scope: Workspace v1 protocol and durable domain foundation  
Final verdict: PASS

## Independence

The audit independently inspected the repository diff, protocol validator,
revision manifests, persistence implementation, tests, and roadmap wording.
It did not treat the implementation plan or existing architecture as an
unquestionable premise.

## First-pass blocking findings

1. **A1 — revision precision:** `WorkspaceDocumentV1.revision` was encoded as
   a JSON number and could lose CAS identity in JavaScript above `2^53 - 1`.
2. **A2 — non-lossless export:** export hashed approved raw bytes but returned
   only a parsed JSON value, which could not reproduce the advertised hash.
3. **A3 — truncated rollback ancestry:** rollback searched only the newest 256
   history entries despite the v1 retention contract keeping every revision.
4. **A4 — open persistence channel:** an arbitrary Widget type string could
   persist paths or token-shaped payloads despite the layout-only boundary.

## Resolution verified

- Revisions now use the existing decimal-string `SurfaceRevision` wire type,
  including `u64::MAX` coverage and rejection of JSON numbers.
- Export now returns the exact manifest-approved UTF-8 JSON text and SHA-256;
  tests reproduce the digest from the returned raw text.
- Rollback traverses the complete committed parent chain independently from
  the 256-entry public history response cap. A 257-revision test reaches the
  oldest committed ancestor and creates a new forward revision.
- Workspace v1 now accepts only the explicit 11-value first-party Widget
  allowlist matching the current UI builtin registry. Paths, token-shaped
  strings, and unverified third-party types fail closed. Shared Surface
  validation remains unchanged; registry-backed extension types are deferred.

The audit also confirmed manifest/payload/directory identity checks, orphan
exclusion, fail-closed unknown-major mutation, exact unknown-major raw export,
concurrent CAS serialization, migration prop stripping, and honest Windows
power-loss durability wording.

## Nonblocking follow-up

- **N1 / process:** the process-global Workspace lock correctly protects the
  current single-daemon, single-effective-root model, but it would create
  unnecessary cross-root contention if multiple effective roots are supported
  in one process later. Track this after merge; it is not a correctness defect
  in the present production topology.
