# PR #646 independent audit

Date: 2026-09-01

Scope: issue #620's structured retained-recovery response for generic restore failures.

## Verdict

PASS. Restore failures after a durable `PreRestoreRollback` now expose only its stable backup ID and a recovery category, while conservatively separating pre-swap definite failures from failures after entering the authoritative swap.

## Evidence

- Target backup validation and rollback-backup creation failures remain unchanged and never claim that a recovery backup was retained.
- Private staging preparation failures map to `BackupRestoreFailed`; the authoritative data root has not entered the swap.
- Once either swap helper is called, failures map conservatively to `BackupRestoreOutcomeUnknown`, including final directory synchronization and post-restore verification failures.
- The outcome-unknown test hook runs after the real swap and before final synchronization and verification, representing an actually changed but not fully confirmed authoritative state.
- Both new errors remain HTTP 500 responses. Their public envelope contains only stable `code`, `recovery`, and the internally generated `backup_id`; original error details and paths remain server-side.
- Workflow tests prove that returned IDs resolve to complete `PreRestoreRollback` manifests, and existing tests prove those backups can restore the prior state.
- The implementation does not wrap `create_backup_locked` publication failures, preserving issue #644's separate boundary.
