## 2. CodeRabbit 阻塞项修复（B1–B11）

### B1 — Coordinator mutex 串行化 read-persist-commit（Major1）

**严重度**：阻塞（并发写可造成盘-内存不一致）

**位置**：`engine/src/daemon/handlers/provider_routing.rs` + `engine/src/daemon/handlers/plugin_tools.rs`

**问题**：`update_providers_endpoint` / `update_routing_endpoint` / `upsert_plugin_tool_endpoint` / `delete_plugin_tool_endpoint` 四个写 handler 没有串行化 read-persist-commit，并发请求可造成盘-内存不一致。

**修复**：在 `DaemonState` 新增 `provider_routing_update: tokio::sync::Mutex<()>` 与 `plugin_tools_update: tokio::sync::Mutex<()>`，四个 handler 在 read-persist-commit 全程持有锁。

**证据**：`cargo test --lib` 1048 passed，含 `provider_routing` 与 `plugin_tools` 模块测试。

---

### B2 — SSRF 控制：https host 解析到内网 IP 即拒绝（Major2）

**严重度**：阻塞（SSRF 漏洞）

**位置**：`engine/src/plugin_tool.rs:225-286` `validate_webhook_url`

**问题**：原实现 `https://` 任意 host 都允许，攻击者可用公网 DNS 指向内部 IP 进行 SSRF。

**修复**：
- 字面量 IP：`parse_literal_ip` + `is_internal_ip` 拒绝 loopback/private/link-local/unspecified/broadcast/documentation。
- 域名：`resolves_to_internal_ip` 解析所有 A/AAAA 记录，任一为内网即拒绝。DNS 解析失败时保守允许（避免暂时故障阻断合法 webhook）。
- `http://` 仅允许字面量 loopback（`localhost` / `127.0.0.1` / `[::1]` / `::1`）。

**证据**：`validate_webhook_url` 单元测试覆盖内网 IP 拒绝、loopback 允许、https 域名解析路径。

---

### B3 — TOCTOU：执行前重新校验 canonical 路径（Critical1）

**严重度**：阻塞（TOCTOU 路径遍历）

**位置**：`engine/src/plugin_tool.rs:call_script`

**问题**：`validate_script_path` 在配置 upsert 时校验一次，但执行时文件系统可能已被替换（symlink/重命名），导致路径遍历。

**修复**：在 `call_script` spawn 之前重新 `canonicalize` 并校验 canonical 路径仍在 `data_root/plugins/` 下。`validate_script_path` 在 upsert 时校验一次（配置校验），`call_script` 在执行时第二次校验（执行校验）。

**证据**：读 `call_script` 源码，canonical_plugins + canonical.starts_with 校验在 spawn 之前。

---

### B4 — 并发 stdin/stdout/stderr + bounded reads（Critical2）

**严重度**：阻塞（pipe buffer 满导致超时假死 + unbounded read 内存耗尽）

**位置**：`engine/src/plugin_tool.rs:call_script`

**问题**：原实现先同步写 stdin 再 wait，子进程因 pipe buffer 满而阻塞导致超时假死；stdout/stderr 用 `read_to_end` 无限制读取可耗尽内存。

**修复**：
- 先取出 stdin/stdout/stderr 管道（`child.stdin.take()` 等），避免 `child.wait()` 与之冲突。
- stdin 写入、stdout/stderr 读取、child wait 并发执行（`tokio::spawn`）。
- stdout/stderr 读取使用 `take(MAX_OUTPUT_BYTES + 1)` 限制内存，超限即报错。
- 超时时 `child.start_kill()` + `child.wait().await` 清理子进程。

**证据**：`cargo test --lib` 1048 passed；读 `call_script` 源码确认并发 spawn + take 限制。

---

### B5 — PluginTool name/description 一次性 leak（Major3）

**严重度**：阻塞（meta() 每次调用都重复 leak 同一字符串）

**位置**：`engine/src/plugin_tool.rs:PluginTool`

**问题**：原实现 `meta()` 每次 `Box::leak` 工具名与描述，daemon 生命周期内重复 leak。

**修复**：在 `PluginTool::new` 构造时一次性 leak name/description 为 `&'static str`，`meta()` 复用。`call()` 直接调用 `self.call_webhook` / `self.call_script`，避免重复构造 PluginTool（CodeRabbit nitpick）。

**证据**：读 `PluginTool` struct 定义 + `new` + `meta` + `call` 源码。

---

### B6 — 凭据文件 0600 权限（Major4）

**严重度**：阻塞（凭据 world-readable）

**位置**：`engine/src/provider_routing.rs:save_provider_keys` + `engine/src/plugin_tool.rs:save_plugin_tools`

**问题**：`provider_keys.json` 与 `plugin_tool_headers.json` 含 api_key / Authorization 密钥，未设权限。

**修复**：新增 `restrict_file_permissions(path)` 函数，unix 平台设 0600，Windows no-op。在 `save_provider_keys` 与 `save_plugin_tools` 写盘后调用。失败时仅记录日志，不阻断流程（权限加固是 defense-in-depth，不是安全边界）。

**证据**：读 `restrict_file_permissions` + `save_provider_keys` + `save_plugin_tools` 源码。

### B7 — api_key 三态语义 + headers preserve-on-edit（Critical4）

**严重度**：阻塞（编辑 provider/tool 时凭据被清空）

**位置**：`engine/src/provider_routing.rs:ProviderEntry` serde + `engine/src/daemon/handlers/provider_routing.rs:update_providers_endpoint` + `engine/src/plugin_tool.rs:save_plugin_tools`

**问题**：前端编辑 provider 时只能拿到 `api_key_set: bool`（不能回填真实 key），不修改 key 时发空字符串，后端清空了已有 key。plugin tools webhook headers 同样问题。

**修复**：
- `ProviderEntry.api_key` serde 改为 `#[serde(default, skip_serializing)]`：JSON 省略 → `None`（preserve）；`""` → `Some("")`（clear）；`"xyz"` → `Some("xyz")`（update）。
- `update_providers_endpoint` 加载 existing_keys，对 `None` 的 entry 保留已有 key。
- `save_plugin_tools` 加载 existing_headers，对 webhook headers 为空的 tool 保留磁盘已有 headers。
- 前端 `provider-management.js` 与 `plugin-tools.js`：编辑时 `api_key` / `headers` 输入为空 → 省略字段（preserve）；新增时为空 → `null`（不设置）。

**证据**：`provider_entry_api_key_deserializes_three_states_for_critical4` 单元测试覆盖三态反序列化；前端 `applyEditor` 与 `saveAllProviders` 逻辑读源码确认。

### B11 — warn-before-clearing 凭据（Critical4 配套）
